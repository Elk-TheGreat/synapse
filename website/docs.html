How SYNAPSE works.

The graph model, execution semantics, type rules, debugging, scripting, plugins, project format and code generation. Written for people who want to extend the system, not just use it.

Quick start

SYNAPSE needs Python 3.11+ and a graphical desktop. Install from source in a virtual environment:

git clone https://github.com/Elk-TheGreat/synapse.git
cd synapse
python -m venv .venv
source .venv/bin/activate
pip install -e .
synapse

Open a project directly with synapse path/to/project.synapse. On a headless machine, run xvfb-run -a synapse.

First runPick the Arithmetic template on the welcome screen, press Ctrl + Enter, and watch the console and wires. Then open Loop to see a reusable function called from a loop body.

Run the tests

pip install -e ".[dev]"
pytest

Core concepts

A project contains one or more graphs, a function library, assets and settings. A graph is a set of node instances and directed edges. A node is an instance of a registered node type with typed input and output ports and a parameter dictionary.

An edge carries one value from an output port to an input port. Execution is dataflow: a node runs when its required inputs are available. Graph inputs and graph outputs define the program's interface.

Graph model

The graph package is independent of Qt and of node implementations. A registry is supplied when validating connections or instantiating behaviour, so graphs can be parsed, inspected and tested without starting the UI.

Connections are checked when they are made: the target port must exist, the source type must be compatible with the target type, duplicated inputs are rejected, and cycles are refused. A graph can still be serialised with a missing node type, which lets the UI report a missing plugin instead of losing the project.

Node definition fields

  • Unique type id, display name, description, category and version
  • Input and output port specs, including optional and variadic ports
  • Parameter specs with type, default, choices and validation
  • An async execution function receiving a node context and inputs
  • Optional keywords for library search and a documentation string

Frames and annotations

Frames group nodes visually and move with their contents. They are part of the graph document, not executable. The minimap paints graph bounds and the current viewport; clicking or dragging recentres the view.

Type system

Values are native Python objects. Media values are wrapped in small dataclasses so their type and metadata survive serialisation and wire previews.

TypePython valueCompatibility
booleanboolOnly boolean unless explicitly converted.
integer / floatint / floatNumeric ports accept both; safe conversion is explicit.
string / bytesstr / bytesDistinct; conversion nodes make intent clear.
array / dictionarylist / dictOptional element type on array specs.
image, audio, video, fileWrapped dataclassesCarry bytes, paths and metadata.
object / anyAny / anythingany is a deliberate escape hatch.

Ports can be optional, with defaults applied when no edge is connected. Custom types can be registered by plugins. Invalid values raise a ConversionError with the expected and actual type; the executor reports the node and port instead of a generic failure.

Execution

Executor builds a run from a graph snapshot, resolves dependencies and schedules nodes as their inputs become available. Independent branches execute concurrently. Blocking work is moved to a thread pool and awaited with asyncio.wrap_future.

Guarantees and limits

  • Validation happens before execution; an invalid graph returns errors without running nodes.
  • Runs can be cancelled; resources registered by nodes are cleaned up.
  • Global timeout, per-node timeout, maximum steps and loop iteration limits prevent freezes.
  • Fail-fast mode aborts on the first error; otherwise independent branches can finish and errors are collected.
  • Per-node results are cached within an executor instance where safe.

Events

The engine emits node start, node finish, debug pause, error and run-level events. The desktop UI re-emits them through Qt queued connections, so the canvas, console and debugger update without blocking the event loop.

ExecutionResult
  status: "ok" | "error" | "cancelled"
  outputs: {port_name: value}
  nodes: {node_id: NodeResult}
  errors: [ExecutionError]
  summary(): human-readable run report

Debugging

Toggle a breakpoint on a node from its context menu or the inspector, then start a debug run. The session pauses before the node executes and exposes its inputs, outputs (when available), the accumulated trace and the current variables.

  • Pause / resume without restarting the graph.
  • Step over the next node and inspect the result.
  • Stop cancels the run and releases resources.
  • Trace history records node, status, duration and output preview.
  • Live wires display a compact preview of the value after a node finishes.
Why it is differentThe debugger is not a separate interpreter. It sits on the same execution path as a normal run, so what you inspect is what actually happened.

Functions

Select a group of nodes and choose Convert to function. Edges that cross the selection boundary become typed function inputs and outputs. The selected nodes move into a new graph stored in the project's function library, and the caller is rewired to a function-call node.

Functions have a name, description, version, typed parameters, return ports and their own internal graph. They appear in the node library and can be called from any graph in the project, including from other functions.

  • Function inputs are available as graph_input nodes inside the function.
  • Function outputs are declared on the function and produced by graph_output.
  • Extraction is structural: review generated inputs, outputs and names afterwards.
  • Functions are project-scoped; graph JSON import/export is supported, but a separate function-library exchange format is not yet provided.

Scripting & security

Script nodes embed Python source in the graph. The UI provides an editor and a test run. At execution time the script receives a JSON payload of its inputs through a separate interpreter:

python -I script.py

The isolated interpreter ignores user site-packages and environment-based startup hooks. A timeout, output size limits and an import allow-list are enforced by the runner. Script errors are returned to the node, including the traceback, and do not take down the application.

Trust boundaryThis is a guard rail, not an operating-system sandbox. A malicious script running as your user may still reach anything your user can reach. Run untrusted projects in a container or a dedicated account.

File, process, network and script permissions come from project settings. File nodes are restricted to configured roots when a policy is active; network nodes can be limited to an allowed-host list. The AI nodes read their API key from an environment variable and never store it in the project.

Language engines implement a small plugin interface: a runner receives source, inputs and options, and returns JSON-compatible outputs or a structured error. Python is the implemented engine; the interface is designed for future JavaScript or Rust integrations.

Plugins

A plugin is a folder with a plugin.json manifest and an entry module. It can declare nodes, categories, configuration fields, dependencies, documentation and a compatible SYNAPSE version range.

{
  "name": "text-tools",
  "version": "1.0.0",
  "api_version": 1,
  "entry": "nodes.py",
  "description": "Text transformation nodes"
}

The entry module defines register(registry, api) and registers node definitions through the plugin API. Plugin nodes are namespaced as ext.<plugin>.<type_id>, cannot overwrite built-ins, and are loaded only when enabled.

  • Discovery scans the bundled directory and the user plugin directory.
  • Install accepts a local package through the plugin dialog; it is not fetched automatically.
  • Enable / disable controls whether its nodes enter the registry.
  • Compatibility checks the manifest's API and host version before loading.
  • Failure isolation reports a broken plugin without preventing the app from starting.

Python plugins run in-process and are trusted once enabled. Script-runtime plugins execute in the isolated runner. Bundled plugins cannot be removed; disable them instead.

Project format

A .synapse file is versioned JSON. It contains project metadata, settings, graph documents, function definitions, assets and dependency declarations. Unknown fields are preserved where practical so newer projects fail with a clear version message rather than silently losing data.

{
  "format": "synapse-project",
  "version": 1,
  "metadata": {"name": "Demo", "description": "..."},
  "settings": {"allow_network": false, "allow_scripts": true},
  "graphs": [{"id": "g_main", "name": "Main", "nodes": [], "edges": []}],
  "functions": [],
  "assets": []
}

Autosave writes a recovery copy while there are unsaved changes. On the next launch, a crashed session offers recovery; discarding it removes the recovery file. Recent projects and UI settings live in a local SQLite database, not in the project.

See the full project format specification for every field.

Code generation

The graph and the executor share one intermediate representation. JSON export writes the graph document plus functions and metadata. Python export produces a standalone script that embeds the compiled IR and drives the SYNAPSE runtime.

This is deliberately not a claim of idiomatic translation. Nodes without a native lowering are listed in the generated file header, and the program reports unsupported constructs instead of silently changing behaviour.

python examples/exported_arithmetic.py --pretty
# {"status": "ok", "outputs": {"product": 42}}

JavaScript generation is not implemented. The IR and the compiler boundary are designed so additional targets can be added without changing the graph editor.

Current limitations

  • JavaScript code generation is not implemented; Python export drives the embedded runtime.
  • AI nodes require an OpenAI-compatible endpoint and an API key in an environment variable.
  • Script and plugin isolation is a guard rail, not a hardened OS sandbox.
  • Functions are stored per project; there is no separate function-library import/export yet.
  • The test suite exercises representative nodes in every category, not every parameter of all 108 nodes.
